## 1. Goal (read this first)

**Problem.** We want a fast text-to-image model that takes an **alpha matte** (a grayscale image: white = opaque, black = transparent) plus a caption, and generates the **foreground RGB, composited on a flat 50% gray background** (RGB = 128,128,128 / 0.5 in [0,1]), so that the generated object exactly fills the matte. Combined with the input matte, that output gives a full RGBA image (the gray background is known, so the foreground color can be recovered by un-compositing).

**Base model.** SANA-Sprint (NVlabs, arXiv 2503.09641), a 1–4 step distilled DiT. We pick it because it is very fast, so many eval runs are cheap.

**Data.** MAGICK (Burgert et al., CVPR; https://ryanndagreat.github.io/MAGICK/, https://huggingface.co/datasets/OneOverZero/MAGICK). This is a large captioned RGBA dataset. A 2023-era diffusion model generated it, so the image quality and captions are dated ("very 2023 quality").

**Method: the AnimateDiff domain-adapter trick, used for in-context control.**
1. **Adapter model**: fine-tune SANA-Sprint (LoRA at the highest rank that fits VRAM, or full fine-tune) on MAGICK images composited on gray, with MAGICK captions. This absorbs the *domain*: gray backgrounds, MAGICK's dated look.
2. **Control model**: bake the adapter into the weights. On top of that, train matte control **based on GateControl** (arXiv 2603.27666, "Gated Condition Injection without Multimodal Attention"; user chose it, m00231: "it's official"). GateControl targets linear-attention models like SANA. The matte is a clean (noise-free) condition; the loss is on the generated image only. Exact architecture: see §5 (from research agent 6).
3. **Final model (inference only)**: `W_final = 1·W_base − 1·W_adapter + 1·W_control`, which is `W_base + (W_control − W_adapter)`. Only the control delta is added to the clean base. In theory this subtracts MAGICK's dated domain "junk" and keeps SANA-Sprint's quality. This is what AnimateDiff did when it adapted video from image data.

**Rationale.** Training the control behavior directly on dated data would also teach the dated look. The adapter soaks up the domain shift first, so the control delta contains (ideally) only "follow the matte".

## 5. Research Findings

From the 2026-11-17 sub-frenzy (5 Sonnet agents). The raw reports are in `agents/.scratchpad/frenzy/`, which is not saved, so the key facts are copied here.

**MAGICK dataset.** 148,193 RGBA PNGs, 1024², 191 GB, straight (not premultiplied) alpha. Path `images/{page_id[:2]}/{page_id}.png`. Index `magick_index.tsv` (read with `quoting=3`); columns `page_id, sim_score, color, nsfw, subject, tag_idk, picked`. Caption = `subject` (short phrase). 3,000 are nsfw. `load_dataset` fails; use `hf download OneOverZero/MAGICK --repo-type dataset --local-dir MAGICK`. Some green spill in hair: filter by `sim_score`.

**Training SANA-Sprint.** No report of a working plain flow-matching LoRA on the Sprint student. The maintainer "never tried" a diffusion loss on Sprint (Sana issue #256). The diffusers script `examples/research_projects/sana/train_sana_sprint_diffusers.py` (sCM+LADD) is merged, full fine-tune only, and inits the student from the teacher. Teacher differs from stock SANA: TrigFlow, dense time embedding, QK RMSNorm. Teachers: `Efficient-Large-Model/Sana_Sprint_{0.6B,1.6B}_1024px_teacher_diffusers`. Inference defaults: 2 steps, `max_timesteps=1.5708`, `intermediate_timesteps=1.3`, guidance 4.5. Fixed noise: pass `latents` of shape (B, 32, H/32, W/32) with `use_resolution_binning=False`. **→ Teacher-first, distill last.**

**AnimateDiff adapter.** LoRA on self- and cross-attention, MSE loss on single frames, base frozen, scale 0 at inference. Evidence is qualitative (paper Fig. 6). Closest precedent for `base − adapter + control`: lllyasviel's ControlNet transfer `Any3 + SD15_control − SD15`; task arithmetic (Ilharco et al.). No direct report of this exact recipe. **Do all weight arithmetic in fp32 from stored originals; round to bf16 once at the end.**

**In-context conditioning on SANA.**
- SANA has **no positional encoding** (position comes from the 3×3 depthwise conv in Mix-FFN). RoPE-shift sequence concat (Kontext, OminiControl, UNO) does not apply. Use a **wide canvas, clean matte on the left**.
- Timestep is one scalar per sample. Per-token timestep is not required: the Kontext pipeline gives clean context tokens the same scalar timestep and slices the output. LTX and Diffusion Forcing use per-token t, clean = 0 (upgrade path).
- **Loss on target (right-half) tokens only**, as in LTX and Kontext.
- GateControl (arXiv 2603.27666): condition control on SANA-1.6B, LoRA rank 16. Plain concat converges slowly on spatially aligned tasks; a 0.09M-param gate speeds it up >10×. **Chosen as our control method (m00231).**
- **GateControl details (agent 6, from the official code https://github.com/Carol-lyh/GateControl, Apache-2.0, no weights):**
  - The condition is a **second token stream**: same VAE, same `patch_embed`, same 20 blocks and weights, its own residuals. No canvas, no positional trick; alignment is learned.
  - Both streams get the same adaLN modulation and the **same timestep** as the noisy latent (condition is clean, not t=0). Text cross-attention and FFN run per stream. Only linear self-attention sees `[cond; x]` (bidirectional).
  - Gate per block: two `Linear(2240, 1)`, ~0.09M params total. `g_x = sigmoid(W_x(LN(x_in)))`, `g_c = sigmoid(W_c(LN(c_in)))`, LN non-affine on the modulated pre-attention input. x stream gets `g_x·attn_x + g_c·attn_c`; cond stream gets its attention ungated. Init zero → 0.5 each (not identity to the base).
  - Base frozen. Trained: LoRA rank 16, alpha 16, on `proj, linear_1, linear_2, linear, to_q, to_k, to_v, to_out.0, conv_point, conv_inverted, proj_out` + gates.
  - Loss: flow matching, target `noise − x0`, logit-normal weighting, target stream only. Condition dropout 0.1 (cond K/V zeroed, gate term ×0), text dropout 0.1.
  - Training: 4× H200, batch 16/GPU (64), bf16, Prodigy lr 1, wd 0.01 (0 on gates), 500 warmup, 10K steps for aligned tasks, 10K images. Inference 20 steps, CFG 4.5; ~2× tokens per forward.
  - Paper: ">10× faster convergence on spatial tasks" (curves, not a table). Canny@512 F1 0.26 vs OminiControl-SANA 0.23. Ablation: gating after cross-attn or plain addition is unstable.
  - Reuse: `train_sana_gatecontrol.py` works on SANA. Deps: diffusers, peft, accelerate, datasets, prodigyopt, transformers, cv2 (diffusers version unpinned). It never passes `guidance`, so Sprint (guidance-embedded, TrigFlow) needs changes.
  - **Fit with our weight arithmetic:** the adapter stays frozen while the control trains, so `W_control − W_adapter` is exactly the control LoRA delta. The final model = base + control LoRA + gates. The gates are new modules, not weight deltas; they are kept as they are.
- SDEdit-style re-pasting on a model not trained with a clean left half is weak (In-Context LoRA). Use re-pasting only as a diagnostic.
- Reported LoRA ranks: 4 (OminiControl) to 512 (UNO); 16 is typical. Steps: 5k (In-Context LoRA) to 100k (EasyControl); aligned tasks ~50k (OminiControl).
- Agent's suggested first design: 1024×512 canvas (16×32 latent tokens) for fast iteration, matte replicated to 3 channels, each half VAE-encoded separately, shared scalar t, rank-16 LoRA on all linears. Seam behavior through the Mix-FFN conv is unverified.

**Step 5 plan (research agent, 2026-11-17 6:40 AM; full report was in `agents/.scratchpad/frenzy/distill_plan.md`).** Teacher and Sprint student have the same architecture except `guidance_embeds` (student only) and `timestep_scale`. ## 13. Trimask model (m00644) — second model class

**Training mix: 30% solid outlines, 70% trimasks (m00718, m00720, m00721; requirement).** Two extra methods, `original` (the MAGICK alpha itself) and `threshold` (alpha ≥ 0.5, solid), together get 30% of training draws (15% each); the 19 trimask methods share the other 70% uniformly. **Why (user, verbatim): "we need to make sure that it masters single outlines. It's a very common use case."** Before 2026-11-19 no method was the plain mask (every method was banded/coarsened by `finalize()`), so the model never saw a solid outline. `threshold` breaks the consistency rule at soft edges (white where alpha < 254/255) and is exempt by the user's explicit request; `original` passes it by definition.

**Goal.** A second model whose condition is a **trimask**: white = surely object, black = surely background, gray (0.5) = unknown/fuzzy, where the model decides. Same target (RGB on 0.5 gray), same method (control on the adapter, then W_base + W_control − W_adapter, run on Sprint). Second journal page, second web demo model class with gray brush + dilate/erode tools.

**Data (BlueJay).** One shared table `trimask_augmentations`, keyed (page_id, method, variant): trimask PNG, method tag, hyperparameters (JSON), and its DC-AE latent. Ten augmentation processors, one per strategy, each written by its own Sonnet agent (m00644), all writing to that table; one shared GPU processor `encode_trimask` encodes them (DRY). Each method runs on its own deterministic subset of train images (about 25k per method), never the eval or showcase-held-out items. Sparrow view `view_trimasks` shows matte vs trimasks per method.

**Four more methods (m00648), one Sonnet agent each:** `combo_union` (unknown = union of the unknown regions of 2–3 random other methods), `combo_chain` (one method's trimask, then a second method applied only to its sure regions), `skeleton_strokes` (sure-white only on thin strokes along the medial axis of the object, sure-black far outside), `partial_view` (a random half-plane or wedge of the image entirely unknown, the rest exact). Two more (m00649): `bilateral_blur` (edge-aware: the unknown band follows image edges, from a bilateral/guided filter of the matte guided by the RGB image) and `random_stack` (2–4 other methods applied in a random order, each overlaid on the result). Three more (m00651): `perlin_warp` (distorted-glass warp of the matte by a Perlin-noise displacement field; unknown where the warped and true shapes disagree), `op_chain` (a randomly chosen and shuffled chain of primitive operations — dilate, erode, open, close, blur, quantize, warp, noise — applied literally one after the other to the running mask), `glass_ripple` (refraction-like ripple distortion: sinusoidal or radial displacement). All nineteen are used in training.

**Ten strategies (method tags).** `morph_band` (erode/dilate band), `noisy_band` (band width modulated by smooth noise), `blur_quantize` (blurred mask cut into 3 levels), `scribbles` (sparse user-like strokes, rest unknown), `bbox_unknown` (unknown = bounding box minus eroded core), `convex_hull` (unknown = hull minus core), `grid_coarsen` (low-res cells that straddle the edge are unknown), `polygon_simplify` (coarse polygon tracing, band around it), `unknown_patches` (random unknown blobs in and out), `fuzzy_ramp` (continuous distance-transform ramp, not 3-level).

**Correctness (m00647).** No incorrect trimasks: sure-white only on fully opaque pixels (alpha ≥ 1 − 1/255), sure-black only on fully transparent pixels (alpha ≤ 1/255), every soft-alpha pixel gray (fuzzy_ramp: ≥ 0.5 on opaque, ≤ 0.5 on transparent, strictly between on soft). `check_consistent` enforces it in `generate()` (raises), and a full table scan must show 0 violations before training. **No pixel-level detail (m00652):** correctness must not be reached by carving the trimask pixel by pixel along the alpha (that leaks the exact silhouette, hair strands and semi-transparent speckle into the condition). Each method makes coarse sure regions that are correct by construction (sure-white inside an opening/erosion of the opaque region, sure-black inside an opening/erosion of the transparent region, any forced gray grown by a disk and smoothed, tiny sure islands and tiny gray specks removed). A per-method detail metric (sure-region boundary length and connected-component count vs the method's own shape) and a visual contact-sheet check gate each method.

**Original and threshold (m00718).** Two more methods, the most common inputs a person gives: `original` (the trimask is the MAGICK matte itself, continuous) and `threshold` (alpha ≥ 0.5 → white, else black: a solid silhouette). Neither runs finalize. `original` passes the correctness rule by definition. `threshold` breaks it at soft edges (hair, glass become sure white or black); it is the one method in `trimask.CONSISTENCY_EXEMPT`, because the user asked for exactly that input ("the original mask thresholded ... doing a solid outline is a pretty common task"). Same subset rule and row count as the other methods (TRIMASK_SUBSET, ~17.8k rows each). **Outline share: 30% (m00720, m00721).** Training draws methods by a fixed split, not uniformly: 30% of draws are the solid outlines (`train_control.OUTLINE_METHODS` = `original` + `threshold`, 15% each) and 70% the other 19 trimask methods (uniform among them, ~3.7% each). `train_control.OUTLINE_SHARE` = 0.30. The user's reason, verbatim: "we need to make sure that it masters single outlines. It's a very common use case." Every 250 steps the training log prints the realized outline fraction next to the target, to check the split. This replaced equal weights (each method 1/19) and, briefly, a 2x weight for the two outline methods (~17% together); see concerns.md. A method with no encoded rows makes training raise (it never silently drops a method).

**GPU use and exports (m00650).** While the trimask table encodes, all 8 GPUs do DC-AE encoding (no training at the same time); the trimask runs start only after. From now on only the λ web versions (`-int4-lambda`) are exported: at λ = 0 they equal the plain int4 output exactly, so plain int4 versions are redundant.

**Multi-resolution training (m00656).** From the next version on, 50% of steps train at 1024² and 50% are split evenly between 768², 512² and 256² (one resolution per step, so a batch is uniform). Latents are precomputed at all four resolutions (m00657) by one hyper-efficient BlueJay encode processor: a long-lived DC-AE server per GPU (loaded once, like generate_eval's servers) that continuously encodes every image and every trimask at 1024², 768², 512² and 256² (area-downsampled), keeping all 8 GPUs busy. Measured DC-AE encode speed on one A100: 1024² 12.9 img/s, 768² 22.9, 512² 51.6, 256² 206 — all four for every row would take ~2.4 h on 8 GPUs, so (1:15 AM decision) MAGICK targets and mattes get all four resolutions, every trimask gets 1024², and a deterministic third of trimask rows (balanced over methods) got 768/512/256 first; at the user's request (m00677, m00678) training was cancelled at 3:39 AM and the other two thirds are encoded too, so every trimask row has all four resolutions before the run starts. Training reads the stored latent for the chosen resolution; low-resolution steps sample only rows that have it. Evals report every resolution.

- **A. ## 16. FIBO2 in the browser (m00688, m00693, m00694)

**Goal.** Run the §14 FIBO2 trimask model in the browser, int4, through the same ONNX Runtime Web + WebGPU stack as §12. The user: "put it into a browser and quantize it" (m00688); "That 4 gigabyte limit, is that something we can change? … It's an open source project after all" (m00693); "let's forge ahead anyway … my MacBook has 36 GB max RAM total, so 4 GB is puny" (m00694).

**The 4 GB limit and the fix.** onnxruntime-web is wasm32: every session's weights pass through a 4 GB wasm heap, and FIBO2's int4 transformer alone is ≈ 4.6 GB. WebAssembly Memory64 (Chrome 133+, Firefox 134+; not Safari) lifts it. ORT removed its Memory64 build option, but its source still has the pieces (`ORT_WASM64` in `onnxruntime/wasm/api.cc`, `wasm/js_post_js_64.js` with PTR_SIZE = 8, PTR_SIZE-aware JS). `web/scripts/build_ort_memory64.sh` builds the same variant npm ships as `ort-wasm-simd-threaded.asyncify.{mjs,wasm}` (WebGPU EP, SIMD, threads), same version as `web/package.json` (1.31.1), with: `-sMEMORY64=1` on every compile (CFLAGS / CXXFLAGS, so all dependencies are wasm64) and on the link (`--cmake_extra_defines CMAKE_EXE_LINKER_FLAGS=…`, because CMake caches env LDFLAGS at the first configure), `-DORT_WASM64`, `js_post_js_64.js`, MAXIMUM_MEMORY 16 GB (Chrome's wasm64 cap), and `-sSIGNATURE_CONVERSIONS` from `web/scripts/ort_signature_conversions.py`: in wasm64 pointers and size_t are i64, which JS must pass as BigInt, ORT's JS passes Numbers, and emscripten converts only the exports listed there (48 signatures parsed from `api.h`, 'p' = pointer-sized; a signature without a 'p' is dropped, emscripten rejects it). One source edit: the external-data loader's JS (`onnxruntime/core/framework/external_data_loader.cc`) converts pointers with `Number(p >>> 0)`, which truncates to 32 bits, so above 4 GB the weights were copied to the wrong address (the 5.37 GB test model loaded but gave all-NaN outputs); the script replaces it with `Number(p)` (exact to 2^53) and fails if any `>>> 0` is left there. Why a script and not a fork of ORT: four flags and one generated list, re-runnable on a new ORT version; the source is cloned fresh (github.com/microsoft/onnxruntime answers 404 from this node, so `MIRROR` defaults to the gitcode mirror of the same tags). Output `web/vendor/ort-memory64/` (git-ignored). The app loads it by pointing `ort.env.wasm.wasmPaths` at that folder with npm's `ort.webgpu.min.mjs` (the `onnxruntime-web-use-extern-wasm` entry), so nothing else changes. Build: ≈ 18 min with 24 jobs on this node.

**Graphs** (`src/sana_alpha/fibo2_web.py`; all inputs/outputs float32, batch 1, so no attention mask: nothing is padded):
- `transformer_g<G>.onnx`: (latents (1,32,LH,LW), cond_latents (1,32,LH,LW), sigma (1,), prompt_embeds (1,6,L,7680), adapter_scale (1,)) → velocity (1,32,LH,LW); normalized latents (`fibo2.normalize_latents`). One call = one model pass: the app runs CFG (two passes against the null prompt) and the Euler step x += (σ' − σ)·v in JS, exactly `fibo2.sample`, so steps and CFG stay user controls (as m00638 asked for SANA). Why not the sampler inside the graph (SANA's choice): FIBO2 needs 2 passes per step for CFG and 20+ steps; a pass-sized graph lets the app pick steps, CFG and σ schedule freely. Dynamic: LH, LW (even, 256–2048 px) and L. The gist-token count is a Python int inside FIBO2's forward (diffusers `compute_gist_count`: text up to 256 tokens → 256 gists, then +64 per step to 512 at 2048 tokens), so a traced graph has one: one graph per count `fibo2_web.gist_counts` (256/320/384/448/512, longest text 256/704/1152/1600/2048 tokens), all sharing one weights file (`web_export.share_external_data`); the app picks the graph by token count. Our JSON captions (≈ 30–80 tokens) always use g256.
- `vae_encoder.onnx` / `vae_decoder.onnx`: FLUX.2 VAE with the BatchNorm (de)normalization inside (`VaeEncoder`: image in [−1,1] → normalized latents, mode; `VaeDecoder`: → RGB [0,1]).
- `text_encoder.onnx`: Qwen3-VL-4B's language model only (text prompts carry no image marker, so no vision tower), cut after layer 35, the deepest FIBO2 reads; the six bundles of three RMS-normalized hidden layers (BriaFibo2Pipeline._get_qwen_prompt_embeds) are computed in the graph. In-browser int4 rather than precomputed embeddings: the user wants free prompts, and one prompt's embeddings are 6 × L × 7680 floats (≈ 95 MB at L = 512).
- Export prerequisites (`make_exportable`): ONNX has no complex numbers, and FIBO2's RoPE is complex (`torch.polar` tables, `view_as_complex`): the table becomes view_as_real (cos, sin) pairs and every attention uses `RealRopeProcessor` (`rotate_real`); RoPE indices cast to int64 (ONNX GatherND takes no int32). Same outputs: difference 0.0 on the tiny model.

**Quantization.** `web_quant`'s SVDQuant weight-only int4 (group 32, rank-32 low-rank branch, smoothing grid) on every linear of the 46 blocks (`fibo2.LORA_TARGETS`, 322 linears) and of the text encoder's decoder layers; norms, embedders and the embedding table stay fp16. `QuantLinear` now follows the input dtype (its scales, smoothing and low-rank factors are cast to x's dtype; MatMulNBits needs its scales in A's dtype): a no-op for SANA's fp16 graphs, needed for the fp32 CPU prototype. Runtime λ: the adapter LoRA itself is the delta W_adapter − W_base, exactly rank 64, so each LoRA'd linear becomes `web_export.LambdaLinear(base, up = B·α/r, down = A)` (`attach_lora_lambda`): no SVD, no approximation, unlike SANA's rank-128 SVD of a full fine-tune's delta.

## 17. Splitter LoRA: RGBA from three backgrounds (m00730, m00731) — FIBO2 first

**Problem.** Every model so far outputs RGB on 50% gray, never alpha. The user: "right now, they are not able to generate alpha … They can only generate RGB."

**Idea (the user's).** FIBO2's last layer `final_layer.linear` (diffusers `transformer_bria_fibo2.FinalLayer`) is Linear(dim, 128): 128 = 2×2 patch × 32 FLUX.2 VAE channels (the user's guess is right). Triple it to 384 outputs: rows 0–127 are the original (object on gray), rows 128–255 and 256–383 start as exact copies, then train them toward the object on white and on black. Initially all three images are identical, so training starts from the current model's behavior. The VAE decoder runs three times. Alpha comes from the three composites; gray is redundant in theory ("you only need on black and on white") and serves as a consistency / uncertainty signal. Later, maybe 9 backgrounds (+ R, G, B, C, M, Y); for now only white, gray, black.
- Name: the **splitter LoRA**, the third LoRA after the adapter and the control. The final layer (the "detokenizer") must be trainable: "Otherwise it will be impossible to distinguish those three from each other."
- **γ (gamma)**: a runtime slider like λ, "how much it splits": γ = 0 gives the current model (three equal images), γ = 1 the trained splitter.
- Start from the newest FIBO2 control checkpoint (≥ 6000), **discard the optimizer** (m00731: Prodigy's state after many steps would make the new objective slow; same rule as m00723).
- Turbo too, as for every FIBO2 checkpoint (§16).
- UI: the RGB view shows the three outputs side by side; RGBA stays; two new views: the alpha matte the model produces from the trimask, and (suggested) the uncertainty.
- Order (m00731): write the code and the BlueJay processors first while `fibo2_tri` keeps training; only when the new pipeline is ready, stop `fibo2_tri`, encode all new samples on all 8 GPUs (white and black composites of every training sample, every resolution), then train. Notify: encoding started, ETA (about one hour in), encoding finished, splitter training started.

**Design decisions (AI, to confirm with the user):**
- **Shared-noise velocity targets.** The model state x_t is the gray trajectory only (input stays 32 channels). Head k predicts v_k = ε − x0_k with the same ε as the gray target (x_t = (1 − σ)·x0_gray + σ·ε). At sampling, integrate the gray ODE as now; any step gives x0_k = x_t + (1 − σ)·v_gray − v_k (ε̂ = x_t + (1 − σ)·v_gray). Decode x0_k from the last step. This adds no tokens and no compute in the transformer.
- **γ** (m00733, the user's correction): the splitter stores a **delta on the tiled base final layer**, never absolute weights. The shipped final layer = tile(W_final of whatever base, 3) + γ·Δ (weight 384 × dim and bias 384, all rows incl. the gray head), plus the splitter LoRA merged with scale γ. So it mixes and matches like the other LoRAs: on dev, turbo or another control checkpoint, that base's own final layer is tripled and the same Δ added; γ = 0 reproduces the base exactly. One shared noise ε for all heads (user confirmed).
- **Alpha and color decontamination: iterative least squares (m00824: "Color decontamination being done jointly with alpha is mandatory"; m00826: "an iterative least squares algorithm is probably the best way to do color decontamination plus alpha ... the only one that could actually get perfect error when doing arbitrary numbers of different background colors").** Pixel space (sRGB in [0, 1], the space of the training composites). Per pixel, the box-constrained least squares min over α ∈ [0, 1], F ∈ [0, 1]³ of Σ_k,c (C_kc − α·F_c − (1 − α)·b_kc)², for K ≥ 2 known background colors b_k ∈ [0, 1]³ (gray levels or RGB). Interpretation recorded (the user named the method, not its exact form): alternating exact 1-D solves, each a block's global optimum: F_c ← clip((C̄_c − (1 − α)·b̄_c) / max(α, ALPHA_ILS_FLOOR), 0, 1), then α ← clip(Σ (C − b)·(F − b) / Σ (F − b)², 0, 1), from the clipped unconstrained linear fit; ALPHA_ILS_ITERATIONS = 32 (16 suffice in validation). Why not the one-shot linear fit + clip used before: clipping α or F leaves a feasible point that is not the constrained optimum (worse on 41–54% of real splitter pixels, §19). The floor matters: at α = 0 F is unconstrained by the data, and F = 0 there stalled α at 0 for some pixels. F is straight (not premultiplied) and decontaminated (the known backgrounds' share is removed exactly); F = 0 where α = 0; uncertainty = RMS residual of the feasible fit. Same algorithm in `fibo2.rgba_from_composites` and `web/src/splitter.js rgbaFromComposites` (per-pixel early stop at |Δα| < 1e-7 in JS). Journal: `journal/alpha_ils/`.
- **Loss**: the same flow loss on all three heads, equal weight.

## 18. Sneak peek: live previews inside every step and every block (m00755)

**Problem.** A generation shows nothing until the VAE decoder runs at the very end; one FIBO2 image takes ≈ 99 s in WebGPU (m00722). The user wants to watch the image form, "very granularly": after every denoising step and after every transformer block, asynchronously, costing at most 10% of the generation time.

**The user's design.**
1. **Tweedie per step.** After each step, the clean-image estimate in latent space x̂0 = x_t − σ·v (rectified flow, §17's convention) is the preview. On by default, but only once decoding it is cheap.
2. **Tiny decoder.** The real VAE decoder is too slow to run per preview. Find or build a decoder 10× to 100× faster with approximate quality (research sub-frenzy).
3. **Per-block shortcut heads.** Each transformer block gets a small head, with a gradient stop on its input, that predicts what the last layer will output (a linear projection; maybe a small conv). It is trained alongside the model but never changes it (stop-gradient). In the app, after each chunk/block the head gives a velocity estimate → Tweedie x̂0 → tiny decoder → preview, all asynchronous.
- Constraints: ≤ 10% slower in total, small VRAM. Tests must show the previews "look right".
- Publish-worthy: "if we ever do publish, this will be something we want to add."
- **Rollout (m00758).** Front end too: a sneak peek switch, ON by default ("when I first see the UI, should have this running off the gate"). Confidence first: "Be very confident that this will work before you implement it, and especially before we train it." Training: the highway is stop-gradient, so it attaches at a splitter checkpoint restart (§17's run starts without it so the GPUs don't wait; the main model's math is unchanged by the attach); attach only after the tiny-model proof (main gradients identical with and without it) and a measured memory/step-time fit for the 8B run.
- **Fast decoder research (m00760).** Tested separately from the highway (it helps either way, through Tweedie). Goal: as fast and light as possible at the best quality: SSIM first ("SSIM is actually even better than LPIPS"), LPIPS, L2. A Sonnet sub-frenzy tries approaches rapidly; a journal report with lossless side-by-side images proves the differences. GPUs: up to 2 for this, the rest train; "at no point should any GPUs be idle" — when the decoder work can't use its GPUs, they run eval work.
- **Residual highway (m00774).** "make it residual so that it can take in the input of the previous sneak peek as well … add some nonlinearities … effectively free": peek_k = peek_{k-1} + f_k(sg(h_k), peek_{k-1}); tested against the plain per-block linear.

**Implementation (fork SneakPeek, 2026-11-20).**
- Objective (m00815): the Tweedie estimate x̂0 = x_t − σ·v the full model would give at that step, not the raw model output; any sample-independent schedule feature is allowed (m00816: anything that lowers the held-out x̂0 error and stays fast).
- **Sneak peek highway** (`src/sana_alpha/sneak_peek.py`, `train_fibo2 --sneak_peek_highway True`): per main block k (44), head_k = Linear(3584 → 128) on the final layer's frozen norm + timestep modulation of the block's image tokens, initialized as the final linear (logit lens), plus a zero-init timestep FiLM (scale, shift from the adaLN conditioning c) and a zero-init Linear(128 → 128) of x_t's own tokens (x_t skip). Inputs detached (stop-gradient), own AdamW (lr 1e-4), loss σ²-weighted MSE to the final layer's output = the x̂0 error. 23.8M params; on the real 8B: main loss unchanged, +1.2 GB, no measurable step-time cost (§19). Residual chain (m00774, `--highway_residual`) tested: no held-out gain, not shipped.
- **Monotone timeline (m00813, m00817):** the plain highway makes a sawtooth (block 0 of a new step is worse than the end of the previous step). The app shows the calibrated blend x̂0_show = w_{s,k}·x̂0_highway + (1 − w_{s,k})·x̂0_{s−1}, w from a per-schedule (step × block) table fitted on held-out generations (w = 1 at step 0; low at early blocks of later steps; 1 at the last block). Measured: removes every jump (§19).
- **Fast decoder:** chosen by the frenzy rounds (§19 lineage); requirement float32 latent (1, 32, LH, LW) normalized → float32 (1, 3, H, W) in [0, 1], ONNX, dynamic H/W. Budget (m00807): per preview ≤ 0.10 × T_total / (passes × 46 + steps) ≈ 105 ms in the user's browser at 1024² for FIBO2, ≈ 5 ms on the A100 (incl. the 0.18 ms head).
- **Learned blend, highway v2 (m00901).** The user: instead of blending after the fact with a fitted table, the highway itself should take in the previous step's Tweedie prediction and noise prediction, plus x_t, and learn how to weigh them, "so that it's structurally impossible for the highway to get worse". It replaces the w table (remedy (b)); the per-block heads stay as trained.
  - Inputs at step s, block k (all 2×2-patchified tokens, 128 channels): h = x_t − σ·v̂_k (the head's own Tweedie estimate), p = x̂0_{s−1} (the previous step's full-model x̂0, CFG-combined as the sampler used it), e = (x_t − (1 − σ)·p)/σ (the previous step's noise prediction ε̂_{s−1}; the Euler step keeps x_t = (1 − σ)·x̂0_{s−1} + σ·ε̂_{s−1} exactly, so e is computed inside the graph and the app passes only p and σ), x_t, and the timestep conditioning c.
  - **Step 1** has no previous step: p = 0, the x_t-only Tweedie estimate E[x0 | x_t] at σ = 1 (the normalized latents have mean 0), so e = x_t/σ.
  - Output: x̂0_show = p + g_k(c) ⊙ (h − p) + R_k([h; p; e; x_t]), with g_k(c) = sigmoid(a_k + G_k·c) per channel and R_k a token MLP 512 → 128 → 128 whose last layer starts at zero.
  - **Never worse at the start:** before training, a_k and G_k are fitted to the current table (g_k(c_s) ≈ w_{s,k}, w clipped to [0.01, 0.99]); R_k = 0. So the untrained v2 is the shipped table blend, and training on the x̂0 error can only lower the loss on its training data from there. Held-out numbers are in §19.
  - **Training is offline, on sampler trajectories** (`sana_alpha.peek_blend`), not inside train_fibo2. A training step sees one noise level, and the previous step's prediction would need a second full forward (≈ +50% step time). Generations of the shipped schedule give exactly the inputs the app has. Target: the generation's final latent (what the preview should look like). Loss: MSE in latent space. Train items: the train split of morph_band and partial_view. Eval: the same 36 held-out items as the table calibration.
  - **Files:** `sneak_peek_blend.safetensors` in the checkpoint's step folder. highway.onnx v2 adds the inputs prev_x0 (1, 32, LH, LW) and sigma (1) and outputs x0 directly; the manifest says `highway.version: 2`. Version 1 (no blend file) keeps the table path, so old versions still load.

## 22. H3 Magic project (second experiment, m00912–m00916, started 2026-11-22 3:00 PM ET)

**Modes (m00912, m00919): autopilot + bulldog + fork mode.** No blocking questions (a question waits at most 60 s, then h3magic decides); never let go of a hard problem; one agent per orthogonal item. Forks only for work that needs the whole conversation's context; simple, well-specified work goes to fresh Sonnet agents with a written brief (m00929).

**Agent name for notifications: "h3magic"** (m00915). Every phone notification starts "h3magic:", gives context, is short, uses no invented jargon, and is written with the human-readable-notification skill (loaded before each send). At most **10** notifications in total (m00912, m00914).

**Goal (m00912).** Eventually an RGBA version of MiniMax H3 (text to video, 480p class). This first pass stops at RGB on a 50% gray background. Method: the same adapter-on-adapter recipe as §1, on H3. Each adapter is a LoRA trained on the model with all earlier adapters **baked in**; at inference the adapters are summed with weights:
`W = W_H3 + a·Δ_pexels + b·Δ_imagegen + c·Δ_graymagic`.
1. **Stock H3** (no adapter): text to video on the 20 eval prompts. Journal row 1.
2. **Pexels adapter** (Δ_pexels): LoRA on stock H3, trained on 10,000 real Pexels clips (first 6 s, 512×512) with H3-style captions. Makes H3 generate Pexels-like video. Journal row 2 (videos).
3. **Image-gen adapter** (Δ_imagegen): LoRA on H3 + Δ_pexels (baked), trained on single frames encoded by H3's VAE as single-frame latents (time length 1). m00917 replaced "the frame at 3.0 s" with **7 frames per clip, at 0, 1, 2, 3, 4, 5 and 6 s** (fence posts over the first 6 s, as augmentation): 70,000 images. The frame at 6 s is the last frame at or before 6.0 s. Makes H3 generate one 512×512 image; should be much faster. Journal row 3 (images).
4. **Gray magic adapter** (Δ_graymagic): LoRA on H3 + Δ_pexels + Δ_imagegen (baked), trained on 10,000 MAGICK images composited on 0.5 gray, 512×512, single-frame latents, with H3-style recaptions of the MAGICK images. Journal row 4 (images).
5. **Video rows** (inference only, 6 s, 512×512, same 20 prompts):
   - 5a "all adapters on": a = b = c = 1 (the ablation: expected low motion).
   - 5b "gray magic only": a = 0, b = 0, c = 1 (hoped: subjects on gray backgrounds with high motion).
   - 5c "Pexels gray": a = 1, b = 0, c = 1 (for fun: maybe Pexels-like video on gray).
   Row 5c by **9 PM ET 2026-11-22** is the deliverable (m00912 second paste).

**Not in scope now:** on-white / on-black channel concatenation (the user considered it, then chose on-gray first); the web UI (unchanged, m00912); audio (excluded everywhere: no audio captions, no audio latents, no audio in the prompt).
